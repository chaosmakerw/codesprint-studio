# 并发：线程可见性、原子性与容量

这份原创资料用于解释一个场景：多个请求同时调用一个延迟较高的模型接口，如何控制共享变量和下游并发。

## 可见性不等于原子性

volatile 可以为变量读写建立必要的可见性和顺序关系，但 counter++ 仍包含读取、加一和写回三个步骤，不是一个原子操作。两个线程可能读取同一个旧值，分别加一后写入同样的结果。简单共享计数可考虑 AtomicInteger；涉及多个变量的不变量，应使用适当的锁或整体状态设计，而不是给每个字段加 volatile。

## 线程池与队列

ThreadPoolExecutor 在典型接收流程中先尝试创建核心线程，再入队，队列无法接收时才尝试扩展到最大线程数，最后进入拒绝策略。因此，采用无界队列时，maximumPoolSize 通常无法按预想解决积压。队列容量、任务超时、拒绝策略和监控应一起设计，不能只调大线程数。

## 限制下游并发

虚拟线程可以降低大量阻塞任务等待时的线程成本，但不会自动限制外部模型服务的并发或额度。可以用 Semaphore 约束正在执行的下游请求，在 finally 中释放已经获取的许可；获取失败不能假装请求成功，也不能释放没有获取的许可。

## 任务结果与超时

CompletableFuture 的组合让依赖关系更清楚，但设置等待超时不等于底层 HTTP 请求被中断。需要分别考虑结果等待、客户端网络超时、取消是否有效、线程池容量和异常传播，不能在失败时返回虚构的成功内容。

## 自己动手

用多个线程累加计数，比较普通变量、volatile 与 AtomicInteger；再把队列设得很小，记录何时出现拒绝。用许可数为二的 Semaphore 包住模拟慢调用，观察同时执行数是否始终不超过二。
